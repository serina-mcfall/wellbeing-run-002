2. THE DECISION TAKEN, AND WHY
-------------------------------
Handover 43.5(b) set out three options.

  (i)   the Supervisor invokes live-gate.js and trusts its decision
  (ii)  live-gate.js is retired and evaluate_merge absorbs it
  (iii) they are kept separate with a tested statement of which is
        authoritative for what

OPTION (iii) IS TAKEN, plus the gaps the comparison found are closed in
the authoritative gate.

Option (i) is NOT AVAILABLE. It requires deciding WHICH REVISION the
JavaScript gate executes from — running it out of the PR's own tree would
let a pull request supply the code that judges it. That boundary is
C-20a(C) and it is still the operator's decision. The handover said so and
nothing has changed it.

Option (ii) is NOT TAKEN. live-gate.js is not redundant: it answers a
different question. It judges a SUBMITTED PR-EVIDENCE PACKAGE — an
untrusted document, where every field is a claim and the whole design is
about not believing any of them. evaluate_merge judges the control
plane's OWN records, written by the Supervisor under its own lock. Porting
package-validation into evaluate_merge would mean validating a document
the Supervisor never receives.

WHAT MAKES THIS HONEST RATHER THAN CONVENIENT: the separation is now
MEASURED. tests/test_c04b_merge_gate_differential.py pins every condition
each gate can report, asserts every one is classified exactly once as
shared / Python-only / JavaScript-only, and requires a substantive written
reason for every JavaScript condition that was not ported. A condition
added to either gate without a decision about the other fails the build.

  HEAD_SHA_UNVERIFIED  — THE MOST SUBSTANTIVE ONE. live-gate.js resolves
                         the head INDEPENDENTLY through git and requires
                         GitHub's observation to agree. evaluate_merge

                         observation disagreeing with git is not caught.
                         Not ported: the Supervisor pushes the branch

                         git call per candidate adds an external call to

                         ACCEPTED DIFFERENCE, recorded not hidden.

  REVIEW_PROVENANCE_* (6) — append-only LEDGER proof that this review is
                         for this commit by that worker. Not ported. The
                         binding EXISTS on the Python side — C-18 stage 5
                         made REVIEW_RESULT carry head_sha and agent_id —
                         but it is never read back at merge time. It would
                         defend against a state.json rollback that the
                         head comparison does not already catch.
                         ACCEPTED DIFFERENCE, and the strongest candidate
                         if these ever converge.

KNOWN DISAGREEMENT ON THE ALLOW SIDE — exactly one:
  live-gate.js requires mergeStateStatus CLEAN exactly. evaluate_merge
  also allows UNSTABLE and HAS_HOOKS, because it separately verifies every
  REQUIRED check BY NAME through gh.checks_state — so UNSTABLE there means
  only "a check nobody required is red", a distinction live-gate.js cannot
  make because it has no required-check list. Pinned by
  MergeStateDifferenceCase, including that a RED REQUIRED check under
  UNSTABLE still denies, and for the CI reason rather than the merge-state
  one.


4. WHAT THE COMPARISON FOUND — THREE FAIL-OPEN HOLES
-----------------------------------------------------
All three were in evaluate_merge, the gate that actually decides merges.
None was covered by any existing test, which is how all three survived.

H1. AN ABSENT OR UNCOMPUTED mergeStateStatus MERGED.
    The gate denied BEHIND, DIRTY and BLOCKED and then fell through to
    "all merge gates satisfied" for EVERYTHING ELSE — including the empty
    string, including GitHub's UNKNOWN, which means "mergeability has not
    been computed yet". Reading "not computed" as "fine to merge" is the
    exact fail-open shape this module refuses everywhere else.

H2. AN ABSENT isDraft MERGED.
    `if pr.get("isDraft")` treats absent as not-a-draft. An observation
    that simply did not carry the field read as ready for review.
    live-gate.js has always refused this (PR_DRAFT_STATE_UNKNOWN).

H3. DIRTY AND BLOCKED SHARED ONE CONDITION TOKEN.
    Two different facts needing two different responses — DIRTY is a
    conflict a Fixer may resolve, BLOCKED is a repository protection rule
    nothing in the control plane can satisfy. C-20a decision D requires
    distinguishable diagnostics; live-gate.js already separated them.

PROVED, NOT INFERRED. routing.py was reverted to its pre-C-04b form and
the differential run:

5. THE FIX, AND WHY IT IS THE SMALLEST ONE
-------------------------------------------
control/routing.py only. Four new condition constants, one explicit
MERGEABLE_STATES allow-list, two edited branches. No new module, no new
parameter, no new call, no infrastructure.

NOTHING WAS WEAKENED AND NO POLICY WAS AMENDED. Every change ADDS a
denial. No denial was removed, no threshold lowered, no verdict rule
rewritten, no gate bypassed. Measured: the full suite was green before and
after, and no existing test needed changing — which is itself the evidence
that nothing legitimate relied on the laxity, and that nothing was testing
it either.

One deliberate restraint: none of the three new denials sets
`invalidate_approval`. A pull request GitHub has not finished assessing
has had nothing change about its evidence, and invalidating the approval
would burn a whole review cycle for an observation delay. Asserted by
test_no_new_denial_invalidates_an_approval.

MERGEABLE_STATES is an ALLOW-LIST, not a longer deny-list, specifically so
that a value GitHub adds in future denies by default instead of merging by
default. That is the property H1 was missing.
