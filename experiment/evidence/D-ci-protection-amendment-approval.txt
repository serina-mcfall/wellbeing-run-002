WHAT THIS DOES NOT APPROVE — THE CEILING
----------------------------------------
This is a REPOSITORY-LEVEL RULE enforced by Run 002's own merge path. It
is NOT:

  * a branch-protection change. Nothing about GitHub's settings changes.
  * a deployment. No App, credential, host user or ownership change.
  * a permanent ban on changing CI. The amendment route exists precisely
    so CI can change, under separate review.
  * approval of decisions A, B or C in §9. Those remain open.

The operator's own framing is explicit that the amendment route exists:
"those changes require a separately reviewed apparatus amendment" — not
"those changes are forbidden".


THE GAP IT CLOSES, AND THE ONE IT DOES NOT
------------------------------------------
C-23 reproduced three ways a product pull request could satisfy the
required `ci` check without CI passing. Two were closed in code (a SKIPPED
or NEUTRAL conclusion accepted as green; a commit STATUS standing in for a
check run). The third - a workflow MODIFIED in the pull request's own
branch, still emitting a green run named `ci` - could not be closed
locally and is what this amendment addresses.

Expected-App pinning does NOT address it and was wrongly offered as a
remedy once: a modified workflow runs THROUGH GitHub Actions, so its check
run carries app_id 15368 legitimately and pinning accepts it. The two
mechanisms address different threats and neither substitutes for the
other.
